## Commands

```bash
npm run dev            # Astro dev server (http://localhost:3000)
npm run build          # production build -> dist/ (Astro Node server + browser islands)
npm run start          # run the built server: node dist/server/entry.mjs
npm run typecheck      # Astro and TypeScript checks
npm run format         # prettier --write . (prettier-plugin-tailwindcss sorts classes)
npm run format:check
npm run db:generate    # drizzle-kit generate — new migration from schema.ts
npm run db:migrate     # apply migrations without booting the app
npm run db:studio      # drizzle studio
npm run generate:onshape-client   # regenerate src/lib/onshapeApi/generated/ from Onshape's live OpenAPI spec
```

Verification: `npm run typecheck`, `npm run format:check`, `npm run build`, then `npm test`. Tests use a disposable database and Playwright Chromium. Install the browser with `npx playwright install chromium`.

## Architecture

Manufacturing workflow tool for an FRC team, built with **Astro** with server-rendered pages and React 19 islands and deployed as a **single self-hosted Docker container**. Parts are pulled from an Onshape CAD Part Studio, "released" onto a kanban board, and tracked through manufacturing processes on shop equipment.

This is a port of [rhr-mfg](https://github.com/FRC2713/rhr-mfg) off Supabase. If you are looking at that repo for reference, the app/UI layer is nearly identical; everything below the data-access modules is different.

### Two data planes

1. **Onshape (external, server API key)** — CAD parts, metadata, thumbnails. Read-only except part-number writes.
2. **Local SQLite via Drizzle** — everything else, plus uploaded images on the filesystem next to it.

There is no per-user DB authorization. Access control requires a Hawk Suite workspace identity from an explicitly trusted, isolated gateway. The Onshape API key only authorizes CAD operations.

### Everything durable lives under DATA_DIR

`DATA_DIR` (default `./data`, `/data` in the container) holds the SQLite file and `uploads/`. A deployment mounts one volume there. Nothing else on disk is stateful.

- `src/server/db/client.ts` — the `db` singleton. Opens SQLite, sets pragmas (**WAL**, `foreign_keys = ON` — SQLite needs the latter per-connection or the junction-table cascades silently do nothing), **runs migrations**, and seeds. Parked on `globalThis` so dev-mode module reloads don't leak handles.
- `src/server/db/schema.ts` — Drizzle tables. **Column properties are deliberately snake_case** so `$inferSelect` produces exactly the row shape the UI was already written against; `src/server/db/types.ts` re-exports those inferred types under the old `KanbanCardRow` / `EquipmentRow` / … names. Keep new columns snake_case.
- `src/server/storage/files.ts` — the local replacement for Supabase Storage. `resolveStoragePath` is the **only** place a user-influenced string gets joined onto the uploads root, and it rejects anything that escapes; don't build absolute upload paths anywhere else.
- `src/pages/api/files/[...path].ts` — serves stored files (splat route; the path arrives as `params.path`).

Timestamps are ISO-8601 **strings**, not SQLite integers, so dates round-trip through the API unchanged.

better-sqlite3 is external in `astro.config.mjs`. The Node image includes production dependencies and the unchanged migration history.

### Migrations

`drizzle/NNNN_*.sql`, generated by `npm run db:generate` from `src/server/db/schema.ts` and **applied automatically on boot**. Commit the generated SQL — an upgrade is just `docker compose up`. Never hand-edit a migration that has shipped.

### Live updates

`src/server/events/bus.ts` is an in-process `EventEmitter`; mutations call `publishKanbanEvent`, `src/pages/api/kanban/events.ts` streams them as SSE, and `useKanbanRealtime` invalidates the cards query. **This is single-process by design** — one container. Running more than one replica needs that module swapped for Redis pub/sub; nothing else would change.

### Auth flow

`src/middleware.ts` gates every page, API, upload, and event stream on Hawk Suite membership. `/signin`, static assets, and GET/HEAD health checks are public. An unauthenticated Onshape iframe receives only a top-level continuation with no shop data.

`POST /api/onshape/webhook` (exact path and method) is the one data route that skips Suite identity, because Onshape can't carry it. It is enabled only when `ONSHAPE_WEBHOOK_SECRET` and `ONSHAPE_WEBHOOK_BASE_URL` are set, checks the secret from its query string in constant time, answers empty bodies (404 for disabled or wrong secret), and does nothing but `partStudioFreshness.changed` (mark that document's workspace Part Studio reads stale) and `onshapeWebhookUpkeep.deliverySeen` (stamp that document's `last_event_at`). Its configuration and callback URL live in `src/server/onshape-webhook.ts`. The gateway must route it without `authorize`; see `docs/ONSHAPE.md#webhooks`. Don't widen the exemption or return shop data from it.

`POST /api/slack/interactions` (exact path and method) is the other one, for Slack's servers. It answers 404 unless `SLACK_SIGNING_SECRET` is set, checks Slack's `v0` signature and five-minute timestamp window (`src/server/slack-interactions.ts`), and only acknowledges: release-message buttons just open links. The gateway routes it without `authorize` too. Don't make it act on a click without adding authorization for the clicking member.

`src/server/suite-identity.ts` follows Hawk Eye's identity-header contract. Enable `HAWK_SUITE_TRUST_PROXY=true` only on an isolated gateway network; configure `HAWK_SUITE_TEAM_ID` and `HAWK_SUITE_ISSUER`. Caddy strips browser identity headers before authorization and injects the approved workspace, Slack user, matching subject, and exact `suite/member` role. Header trust grants nothing by default. Never expose a trusted app port directly.

Local development without the gateway: `HAWK_SHOP_DEV_SIGNIN=true` with `npm run dev` signs loopback requests in as a fixed member (`src/server/dev-identity.ts`; docs/architecture.md#local-development-sign-in). The middleware imports it only under `import.meta.env.DEV`, so a production build contains none of it; it also requires proxy trust off. Keep that import inside the DEV branch, and never add a dev identity path that a built server can reach.

`requireAuth()` reads the verified request identity; Onshape credentials never grant Shop access. Same-origin checks protect every mutation, including multipart uploads. Use `APP_URL` for the browser-facing origin when TLS terminates at the gateway.

Onshape access uses one server-side API key pair (`ONSHAPE_ACCESS_KEY`, `ONSHAPE_SECRET_KEY`, optional `ONSHAPE_BASE_URL`). There is no per-user Onshape connection: every CAD read and write runs as the key's Onshape account. `onshapeFetch` in `src/lib/onshapeApi/auth.ts` is the signing transport; it HMAC-signs each request, refuses non-Onshape hosts, and re-signs bounded redirects (signing and redirect rules: docs/ONSHAPE.md#authentication-and-signing). Only the Onshape gateway calls it; route every Onshape call through the gateway. A missing key pair returns 409, independently of Suite's 401. `/onshape` shows whether the key is configured. `/auth/logout` sends the browser to Suite sign-out. Redirect destinations pass through `safeRedirectPath`.

`src/server/request-context.ts` uses AsyncLocalStorage so server helpers such as `requireAuth()` and `getSessionActor()` read the current request's verified identity.

### Onshape API code

- `src/lib/onshapeApi/gateway.ts` — the Onshape gateway, the one path to Onshape (see the budget section below).
- `src/lib/onshapeApi/generated/` — `@hey-api/openapi-ts` output, **generated, never edit by hand**. Only its types are used, through `src/lib/onshapeApi/generated-wrapper.ts`; types like `BtPartMetadataInfo` come from here. Requests go through the gateway, never the generated SDK functions.

### Data fetching pattern

Astro owns routes, layout, navigation, and the server-rendered overview. Pages call server repositories directly. Each interactive workflow is one React island under `src/components/islands/`, with its own query provider, error boundary, toasts, and live event subscription. Keep drag-and-drop, dialogs, filters, and selection within that root.

`src/lib/api/` is the browser's view of `/api/*`. Keep one fetcher and query key factory per read, and use its shared mutation functions. Components do not fetch directly. Repositories and SQL remain in `src/server/`; browser modules stay client-safe. Type-only imports from repository types are erased. `virtual:hawk-shop/server-only` is enforced by a Vite plugin and fails the build if a server module enters a browser bundle.

Preserve the API's existing JSON payloads so equipment, manufacturing, and connector workflows share the same handlers. `src/lib/api/partActions.ts` intentionally reads a rejected operation's `{ success: false, error }` body as inline validation data. A Suite 401 starts sign-in recovery; a CAD 409 stays in the workflow.

### Thumbnail caching

`/api/onshape/thumbnail?cardId=…` resolves a card's `image_url`, checks `part_thumbnails`, and on a miss fetches from Onshape, writes it under `thumbnails/<hash>.png`, and redirects to `/api/files/…`. When the card (or the connector's `?url=` request) names the part and its microversion, the row is keyed by `partRowKey` (document, element, part, microversion), so an unchanged part never costs a second call and an edited one gets a new image. Onshape's thumbnail href (`/api/thumbnails/<id>/s/300x300`) names no part, so a microversion row only answers the URL it was fetched from; a `?url=` request with someone else's ids costs at most one refetch. A miss goes through the gateway (`onshapeRead`, label `thumbnail`, binary, deduplicated by href), so concurrent misses for one image share one call; the route keeps its own `part_thumbnails` store and files. Image fetches send `Accept: */*`, because the signer's default `application/json` gets a 406. Cards save `onshape_microversion_id` and their thumbnail href at release and keep both: a later workspace edit costs no thumbnail call for a released card. Every proxy URL (`?cardId=` or `?url=`) is built by `thumbnailProxyUrl` in `src/lib/api/onshape.ts`, which is client-safe so server modules use it too. Without a microversion the lookup falls back to `source_url`, and a legacy row (null `microversion_id`) is adopted once for the first microversion that asks. The path is derived from a hash of the key, so **the same part image is shared across cards** — which is why `deleteCardImage` only removes `card-images/` entries and leaves `thumbnails/` alone.

Stored `image_url` values may be legacy proxy URLs (`/api/onshape/thumbnail?url=…`) that get unwrapped.

The route also serves `?url=<absolute Onshape URL>` for the connector, which has a part's thumbnail href but no card yet. That form is allowlisted to `https://*.onshape.com` in `isOnshapeUrl` — the handler signs whatever it fetches with the server's API key, and `onshapeFetch` refuses any other host as a second check.

### Onshape API calls are a hard annual budget

Onshape gives the team a fixed **yearly** API allocation (10,000 requests company-wide), and running out returns **402** until it resets, not a 429 you wait out. Every avoided call is permanent savings, which inverts the usual caching trade-off: staleness is cheap, a miss is not. The Onshape facts behind this, each labeled documented, observed or unverified, are in [docs/ONSHAPE.md](docs/ONSHAPE.md); read it before changing any Onshape call, and update it in the same PR as code that relies on new Onshape behavior.

`src/lib/onshapeApi/gateway.ts` (the **Onshape gateway**) is the chokepoint. A caller describes a read (`onshapeRead`: usage label, optional cache key and TTL or a dedup key, request, JSON or binary response) or a write (`onshapeWrite`); the gateway owns caching, single-flight, the usage tally, the 402 mapping and the daily budget guard. Usage labels are fixed: `parts`, `version`, `thumbnail`, `metadata-read`, `metadata-write`, `webhook-register`, `webhook-list`, `webhook-delete`. Tests substitute an in-memory adapter at its seam (`useOnshapeAdapter`, `tests/onshape-memory-adapter.ts`). Every call site goes through it: parts, version, thumbnail, part-number metadata and webhook management. A successful response is tallied as soon as it arrives, before its body is read, because Onshape charged for it either way. `src/lib/onshapeApi/cache.ts` keeps the key builder, row-level cache primitives and the tally. Two cache layers:

- **SQLite** (`onshape_api_cache`), not memory, so a `docker compose up` does not re-buy every response the team already paid for.
- **In-process single-flight**, so ten browsers opening the board at once produce one upstream call. The SQLite layer cannot do this alone — none of the ten has written a row yet.

`ttlMs: null` means never expires, and that is the right answer whenever the upstream is frozen: parts at `wvm=v` or `wvm=m` are immutable, so Part Studio freshness caches them with no expiry and `ONSHAPE_CACHE_TTL_SECONDS` only governs `wvm=w`. A finite, positive override wins; otherwise the default is 86,400 seconds (24 hours) when `onshapeWebhookSettings()` returns configured settings, or 300 seconds (five minutes) when settings are disabled or invalid. Configuration does not prove production webhook reliability; see `docs/ONSHAPE.md#webhooks`. A failed response (4xx/5xx) is never cached and never counted: Onshape doesn't charge 4xx/5xx, and caching an auth failure would poison the entry for the whole TTL. Expired rows stay in the table for the budget guard.

`src/lib/onshapeApi/partStudioFreshness.ts` (**Part Studio freshness**) answers "may I reuse this Part Studio read?" for the parts route, the release check, card snapshots and the part-number action: `get(partStudio)`, `changed(documentId, elementId?)`, `wrote(partStudio, partId, { partNumber })` and `discard(partStudio)`. It owns the parts key layout and TTLs; never build a `parts` cache key elsewhere. A change event marks workspace reads stale with a floor instead of deleting them: expiry becomes `min(current expiry, max(now, fetched + ONSHAPE_MIN_REFRESH_SECONDS))` (default 300), so a burst of edits costs at most one parts read per Part Studio per window and nothing while nobody is looking. A delivery naming an element marks only that element; one without marks the whole document. An accepted part-number write is applied to the cached read (write-through) and the browser patches its own query data, so the edit costs only its three metadata calls. See `docs/ONSHAPE.md#webhooks`.

`ONSHAPE_DAILY_CALL_LIMIT` is an optional daily ceiling (unset, empty, non-positive or non-integer = no limit) on today's (UTC) tallied calls across all labels. Once reached, a cached read returns its stored answer even if expired, and an uncached read or a write throws `OnshapeDailyBudgetError`, which `onshapeErrorResponse` answers as 503. `onshapeOperation` checks the guard once at the start of a multi-step operation so a part-number write already under way can finish. `/onshape` and `/api/onshape/usage` (`budget`) report the limit, today's count and whether the guard is active.

**The Onshape key is not an auth boundary.** The server holds it for every caller, and a cache hit needs no upstream call at all. `api/onshape/parts`, `api/onshape/version`, `api/onshape/thumbnail` and `api/onshape/usage` all call `requireAuth()` explicitly; a new cached route that skips it answers any caller on the LAN.

`recordOnshapeUsage` tallies `calls` (left the building) vs `hits` (absorbed here) per day in `onshape_api_usage`, readable at `/api/onshape/usage`. Onshape's developer portal shows only a yearly total, which is not enough to find out what is spending the allocation. The `x-rate-limit-remaining` response header is **not** the yearly remaining count (see docs/ONSHAPE.md#remaining-calls-header), so never label it as one.

`onshapeFetch` also saves the final response's `x-rate-limit-remaining` header in `onshape_api_remaining`, one row per `endpointFamily`; it is not the yearly allocation. `/onshape` warns below `ONSHAPE_REMAINING_WARN_AT` (default 1000) and shows a 402 as "allocation used up". The gateway turns a 402 into `OnshapeAllocationExhaustedError` on every path; any other non-OK answer throws `OnshapeRequestError` with Onshape's status and reason.

Card details never call Onshape. Release captures the part's material (`""` when none was set) and its version name onto the card (`onshape_material`, `onshape_version_name`), from the cached parts and version reads it already makes. A card with null values predates this or lost its version read; `POST /api/kanban/cards/:id/snapshot` (`src/server/kanbanApi/cardSnapshot.ts`) fills it once with at most one cached parts read and one cached version read, saves it, and answers unknown (null) without saving when Onshape fails. The client calls it only for such cards.

Anything that adds a new Onshape call belongs behind the gateway. The uncached calls (the part-number metadata read/write on release, webhook management) still go through it for the tally and the ceiling; the part-number write runs inside `onshapeOperation`.

`src/lib/onshapeApi/webhooks.ts` (**webhook upkeep**, `onshapeWebhookUpkeep`) keeps one Onshape webhook per document whose workspace is read (`onshape_webhooks` table). It runs on evidence, never on a clock: boot and quiet days cost nothing. Its inputs are `ensure(documentId)` (after every workspace parts read, not awaited; registers a new document), `deliverySeen(documentId)` (from the webhook route) and `workspaceObserved(documentId, elementId, fingerprint)` (from `partStudioFreshness.get`, only when the gateway's `onSource` reports `upstream`). A list-and-repair pass runs when a Part Studio's parts changed between two upstream reads with no delivery in between, or when the callback URL's stored hash differs from the current one, at most once per 24 hours (`onshape_webhook_upkeep` row). These calls can't be cached. They go through the gateway, obey the daily ceiling, are tallied as `webhook-register`, `webhook-list` and `webhook-delete`, and never run while webhooks are disabled. Registration must never block or fail a parts read.

### Routing layout

`src/pages/` contains Astro pages and typed APIRoute endpoints. `src/layouts/AppLayout.astro` renders the shared branded header, navigation, account disclosure, and skip link. `/` renders the overview on the server. `/kanban`, `/kanban/done`, `/equipment`, and `/onshape_connector` mount contained interactive workflows.

Dynamic endpoint segments use `[id]` and files use `[...path]`. Query parameters on the connector identify its Part Studio; an incomplete scope shows instructions. The embedded entry offers a top-level continuation because Suite cookies use SameSite=Lax. Keep the full connector query in that continuation.

Kanban columns remain a JSON blob in `kanban_config` row `id = 'default'`, with `DEFAULT_KANBAN_COLUMNS` as fallback. Card `column_id` values refer to those ids.

## Conventions

- Import alias is `~/*` → `./src/*`.
- shadcn/ui (new-york, slate) in `src/components/ui/` — regenerate rather than hand-edit; app components live under `src/components/mfg/` by feature.
- Tailwind v4 uses `src/styles/global.css`, with semantic tokens and branding copied from Hawk Eye. Before UI changes, read `docs/BRANDING.md` and `docs/architecture.md`.
- Self-host Barlow headings, Open Sans body text, and Roboto Mono figures. Use supplied team marks and the shared tokens; dark mode follows the OS.
- Server-side data modules start with `import "virtual:hawk-shop/server-only"`. That marker is enforced by the Astro Vite plugin: importing such a module from client code fails the build.
- `src/lib/logger.ts` exists (debug suppressed in prod) but most code still uses `console.*` with a `[SCOPE]` prefix; match whichever the surrounding file uses.
