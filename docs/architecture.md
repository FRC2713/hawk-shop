# Hawk Shop architecture

Shop follows Hawk Eye's Astro architecture. The server renders page layout, navigation, account identity, and the overview. React islands own the manufacturing board, completed cards, equipment and process editor, Onshape part selection, and the phone screens (Next up, Backlog, Shop, My parts and the part page). Each island keeps its existing query cache, drag-and-drop, dialogs, filters, bulk selection, and SSE subscription in one React root.

`src/pages/api/` retains the existing endpoint URLs and payloads. `src/server/` owns SQLite repositories, migrations, storage, and the event bus. `src/lib/api/` contains browser fetchers and shared query keys. The build rejects browser imports of modules marked `virtual:hawk-shop/server-only`.

Equipment add and edit share a camera-first React editor at `/equipment/new` and `/equipment/:id/edit`. `/equipment/:id` is the machine page; `/equipment/:id/edit` remains the camera-first editor. The phone list groups machines under every attached process, with a No process group for unattached machines. It shows the first photo, derived status and Backlog queue size, plus All, Needs maintenance and No photo filters and a floating add link. Process management remains below the list. Rows link to `/equipment/:id`. At desktop widths, grouped tables show machine, status, current part, queued, done this week and SOP. Each table scrolls within its panel. Missing SOPs link to the equipment editor; process management remains below the tables. Photos are resized and re-encoded in the browser to a maximum 2000 px edge, uploaded sequentially, and ordered through `PUT /api/equipment/:id/image` with `{ imageUrls }`. That endpoint accepts a permutation of existing photos only; existing upload, delete and equipment payloads remain supported. The stored `image_urls` order defines the thumbnail. Maintenance actions use the existing maintenance endpoint independently of unsaved form fields.

`GET /api/equipment` adds `machine_status` (`needs-maintenance`, `running`, `idle`) and `queue_size` to each equipment row. `EquipmentListItem` in `src/lib/equipment.ts` is the shared contract. Maintenance takes precedence over a linked In Progress card; other columns do not make a machine running. Queue size uses `machineQueue`, including compatible unassigned Backlog parts, so it matches the machine queue endpoint and excludes running, Review and Done cards. The server reads cards once for the whole list, and card SSE events invalidate the equipment query. The additive `current_parts` field contains `{ id, title }` for every linked In Progress card. `weekly_stats` contains `{ week_start, week_end, done, sent_back }`.

`getMachineWeeklyStats(now?)` in `src/server/equipmentApi/stats.ts` queries status history once for all machines and returns `{ week_start, week_end, by_machine }`, with a `Map<string, MachineWeeklyStats>` keyed by equipment id. Machines absent from the map have zero counts. The list and the machine page can share this server query. Weeks start Monday at 00:00 UTC and end exclusively at the following Monday. Done counts distinct cards moved into Done; sent back counts distinct cards moved from Review to Backlog or In Progress. Repeated transitions count a card once per outcome per week, and a card can appear in both counts. Counts are parts, not quantities, and remain after the card moves to another status. History does not snapshot machine ids, so attribution uses the card's current machine link: reassignment moves its counts, and deleted cards cannot be attributed. No historical machine attribution is inferred. Active maintenance fields record the current problem. Clearing a maintenance flag clears those fields and stamps `equipment.last_maintenance_at`, the durable completed maintenance date. New reports and redundant clears retain that date.

### Machine page contract

`GET /equipment/:id` opens a machine by equipment id, with Suite membership required by middleware. Encode ids as path segments. It returns 404 with a link back to equipment when the id is unknown. The page has one React workflow root, with photos in stored order, name, location, attached processes, derived status, SOP or Add SOP link, Report a problem, and Edit equipment. Missing SOP and Edit equipment both link to `/equipment/:id/edit`. The phone list and desktop table already link here.

The island reads the existing `GET /api/equipment` contract for machine fields, `current_parts` and `weekly_stats`, reusing `getMachineWeeklyStats` through that repository rather than issuing a second stats query. For every current part it reads `GET /api/kanban/cards/:id` for the latest In Progress status-history timestamp and assignee, then `/api/users/:id` for the member name. Time in status updates every minute. No history means unknown time, never the card's last-edited time. Multiple In Progress parts are all shown.

The numbered queue reads `GET /api/equipment/:id/queue`. Up/down controls post the displayed ordered ids to `POST /api/kanban/cards/reorder` with `{ machineId, cardIds }`, then refresh the shared queries. Controls disable while saving, and errors leave the previous order visible. This uses #118's existing member authorization; Suite currently exposes no separate mentor role to enforce. Queue and current-part detail keys share the cards invalidation prefix, so SSE events refresh both.

Report a problem posts `{ note }` to `POST /api/equipment/:id/maintenance`. The server validates the note and records the verified session actor, ignoring caller-supplied reporter fields. It sets the existing maintenance flag and refreshes the page's equipment data; it sends no Slack message. Mark fixed clears the active report and records `last_maintenance_at`. Last maintenance displays this completed maintenance date, retained across later reports, or an empty state when none is recorded. The secondary Delete equipment action loads all cards to count links to this machine, including completed cards, then opens the existing confirmation dialog before deletion. Cancel leaves the machine intact; confirmed deletion returns to the equipment list.

### Shared station display

Equipment's Open station screen link opens `/station`, where members choose a process. `/station/:id` shows all machines attached to that process, ordered by name. Unknown process ids return 404 and offer Change station. Machine names link to `/equipment/:id`. No station table is needed.

`src/components/islands/Station.tsx` owns one workflow root and uses the existing equipment, processes, machine queue, card details and user queries. Current work shows every In Progress part with its assignee, quantity and time since its latest In Progress history entry. Unknown history is shown as unknown. Queues show the first three entries in server order, including compatible unassigned Backlog parts. Idle machines with work waiting have a teal outline and a Work waiting label. Maintenance replaces current work and the queue with the reported problem. SOP links remain available. The display does not load thumbnails, backfill card snapshots or call Onshape.

The workflow's existing SSE subscriber invalidates equipment, queues and current-part details on change and reconnection. All station queries also refresh every three minutes, including in background tabs, to recover from missed events. Elapsed time updates every minute. Query failures are visible beside the affected data. Normal Suite sign-in recovery still applies if membership expires.

`src/layouts/StationLayout.astro` selects the shared layout's station mode, hiding ordinary navigation, phone tabs and the account menu. Only station routes select this mode. Scoped station styles fix the display to a dark Red Hawk layout for 1280×800 and larger, with 18 px body text, 28 px machine names and 56 px controls. More machines than fit across the display scroll horizontally; long queues or multiple current parts scroll inside their column. Each queued part has a Claim action opening `src/components/islands/StationClaim.tsx`, which names the part and machine, shows today's process roster as large buttons, and searches every member who has signed in. Choosing a name first records their presence, then calls the existing claim action with `userId` and `machineId`. A conflict stays visible for recovery. Hold a roster name for 700 ms to request removal, then confirm; keyboard users focus the name and press Delete or Backspace. Cancel and Escape close the picker and return focus to Claim. Each current part has a Done action using the existing In Progress → Review transition. The picker can accept the QR addition in #142.

`GET /api/processes/:id/roster` returns `{ shop_day, members }`. Authenticated same-origin `POST` and `DELETE` with `{ userId }` pick or remove a member for today. The SQLite `station_roster` table has one row per member, process and shop day, including `added_at`. Repeated picks preserve the original added time. Old days remain stored and are ignored by today's query, so rosters survive restarts without a cleanup timer. Roster mutations use the existing event stream; its cards-query invalidation also refreshes roster queries. The picker polls every three minutes, including in background tabs.

`SHOP_TIMEZONE` defaults to `America/New_York` and accepts an IANA timezone. `SHOP_DAY_CUTOFF_HOUR` defaults to `3` and accepts an integer local hour from 0 through 23. Before the cutoff, activity belongs to the previous local calendar date. Date selection uses the local clock and calendar, including DST, rather than subtracting three elapsed hours. Invalid configuration fails roster operations visibly. Changing these values changes which stored day is queried; it does not rewrite history. Restart the container after configuration changes.

Claims and Done from any client, including phones, add the actor to the card's processes in the same transaction as the change. When a machine is attached, only processes shared by the card and machine receive the member; without a machine, the card's processes are used. Claim adds the chosen assignee. Done adds the signed-in member performing the action. Failed actions add no workflow activity. An explicit station pick still records presence even if the following claim loses a race. Claim history stores the picked person in `actor_id`/`actor_name` and the verified signed-in account in the additional nullable `device_id`/`device_name` fields. Existing history retains null device values. The request body cannot supply the device identity.

#### Kiosk setup

Use a shared display at 1280×800 or larger and 100% browser zoom. Open Shop through the Suite gateway, sign in with an approved workspace member, choose Equipment → Open station screen, then choose the process. Bookmark that process URL as the display's startup page. Use the browser's full-screen or kiosk mode and the device's power settings to keep the screen awake. Check that the display can reach the gateway and that its session is signed in before shop starts. Change station switches processes; Equipment exits the display.

Device lockdown, automatic browser startup and automatic sign-in are device administration tasks. Shop does not bypass Suite authentication, extend token lifetimes or prevent the operating system from sleeping. If the Suite session expires, sign in again. Maintenance labels are informational and do not physically disable equipment.

SQLite, its ordered Drizzle migrations, and uploaded images retain their existing format and location under `DATA_DIR`. This migration does not replace the database or renumber existing users. The historical `users.onshape_user_id` column accepts Suite subjects for new Suite users; existing Onshape users remain available for historical assignment and submitter display. Cards created after migration record the verified Suite subject as submitter. Changing assignee leaves submitter intact.

## Authentication

The Suite gateway strips caller identity headers, authenticates the approved Slack workspace, and injects the same identity headers Hawk Eye reads. Shop validates the team, Slack user, subject, and exact `suite/member` role on every request. `HAWK_SUITE_TRUST_PROXY` defaults to false. Enabling it requires an isolated app network and a gateway that strips and replaces identity headers. An arbitrary caller able to reach the trusted app port could impersonate a member.

### Local development sign-in

Without a gateway, set `HAWK_SHOP_DEV_SIGNIN=true` in `.env` and run `npm run dev`. Every request from a loopback client (`127.0.0.1` or `::1`) is then signed in as the fixed member `slack:TLOCALDEV:ULOCALDEV` ("Local Developer"), defined in `src/server/dev-identity.ts`. Open the app at the `APP_URL` origin (default `http://localhost:3000`) so the same-origin check on writes passes. Signing out has no effect while the flag is on; remove it to see the signed-out screens.

It fails closed. The middleware imports the module only inside an `import.meta.env.DEV` branch, so `npm run build` drops it and the built server ignores the variable. It never applies when `HAWK_SUITE_TRUST_PROXY=true`, so gateway headers and the dev identity never mix, and it never applies to non-loopback clients, so `astro dev --host` does not sign in the LAN. `tests/dev-identity.test.ts` checks the build output contains none of it and that a built server with the flag set still refuses access.

Health checks, static files, and the embedded connection exchange remain public. Every data endpoint, uploaded image, live event stream, and mutation requires Suite membership, with two exceptions. `POST /api/slack/interactions` (exact path and method) receives Slack's button clicks: it is disabled without `SLACK_SIGNING_SECRET`, verifies Slack's request signature, returns no shop data, and only acknowledges. The other is `POST /api/onshape/webhook` (exact path and method), which Onshape calls without a Suite identity. It is enabled only when `ONSHAPE_WEBHOOK_SECRET` and `ONSHAPE_WEBHOOK_BASE_URL` are set, checks the secret in its query string, returns no shop data, and only clears that document's cached workspace reads. The gateway routes that exact path and method to the app without `authorize` (the `@shop-onshape-webhook` matcher in [ONSHAPE.md](ONSHAPE.md#webhooks)); everything else still goes through it. Same-origin checks cover JSON and multipart writes. Responses containing shop data are private and not cached by shared proxies.

CAD access uses one server-side Onshape API key pair (`ONSHAPE_ACCESS_KEY`, `ONSHAPE_SECRET_KEY`). Every request is HMAC-signed in `src/lib/onshapeApi/auth.ts`; the signing transport refuses non-Onshape hosts and re-signs bounded Onshape redirects. Users never connect an Onshape account, and the key never reaches the browser. Local cards, assignments, processes, equipment, uploads, and board configuration work without it. CAD operations report a missing key pair with HTTP 409; Suite session failures use HTTP 401. `/onshape` shows whether the key pair is configured.

All CAD reads and writes share the key's Onshape permissions, so its account should see only the robot documents. Existing disk caching and API usage accounting remain intact.

## Deployment handoff

`deploy/hawk-suite-auth.patch` contains the companion changes for the existing Hawk Suite authentication overlay. Review and apply it in the Suite repository before deploying this Shop image. It gates Shop through Suite, passes the approved workspace settings to Shop, and retains public health checks. It does not change Suite's pinned production release or deploy anything.

The iframe-only connector entry renders a connection screen without shop data when Suite identity is absent. A click opens `/auth/embed/authorize` in a popup. The gateway requires the ordinary top-level Suite session on that route, clearing any caller Authorization header and ignoring the embedded cookie. After sign-in, Shop returns a random, single-use code bound to the iframe's SHA-256 proof challenge. The popup sends the code only to its same-origin opener. The iframe checks both the message origin and popup window, then posts the code and verifier to the exact `/auth/embed/exchange` endpoint. The exchange requires Shop's browser Origin and JSON, expires codes after 60 seconds, and consumes them once. Codes live only in this single server process; restarting it requires reconnecting.

The exchange sets `__Host-hawk-shop-embedded`, a host-only `Secure; HttpOnly; SameSite=None; Partitioned` cookie with an eight-hour maximum lifetime. It contains the existing signed Suite access token. Caddy validates that token on every request using the same signing key, issuer, audience and membership role as the ordinary Suite session, and injects the usual identity headers. Shop never treats a raw embedded cookie as identity. The gateway returns authentication errors for API calls rather than redirecting fetches into Slack; an expired iframe navigation returns the connection screen with identity cleared. The shared Suite cookie stays SameSite=Lax. The embedded copy can remain valid until its cookie or signed token expires after signing out elsewhere, just like a copied bearer token; signing out through Shop clears the current partition's copy. No refresh token is copied.

The connector permits embedding only by itself or HTTPS Onshape subdomains using CSP `frame-ancestors`. No Onshape API key, Suite token, or refresh token enters page scripts, URLs, postMessage payloads, or JavaScript-readable storage. Browsers that block partitioned cookies show a connection error instead of a sign-in navigation loop. Onshape must allow popup windows from its iframe. The full Part Studio query stays in the original frame throughout connection and release.

Deploy the Shop image together with the Suite embedded-session routing changes. A Shop-only upgrade cannot authenticate iframe requests through an older gateway. See [embedded authentication](EMBEDDED_AUTH.md) for validation and rollout details.

The image now runs Node 24 and Astro's generated server entry at dist/server/entry.mjs, produced by `npm run build`. Preserve the existing `/data` volume. Starting the image without Suite configuration leaves health checks available and returns a setup error for data requests.

## Verification

Run `npm run typecheck`, `npm run format:check`, `npm run build`, and `npm test`. Install Chromium once with `npx playwright install chromium`.

The tests start the production build with a temporary SQLite database and fixture gateway identity. They exercise authentication rejection, safe login redirects, same-origin writes, card and equipment CRUD, assignment, quantities, column configuration, multipart images, SSE, cached CAD access, and browser hydration in desktop light and mobile dark themes. They do not call the live Onshape API or modify production data. The companion Suite patch was also exercised in a disposable Suite Caddy routing fixture. Re-run the Suite repository's checks when applying it to a newer Suite revision before deployment.
